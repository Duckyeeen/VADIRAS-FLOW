# MASTER PROMPT — ANTIGRAVITY
## Vadiras Flow Backend Prototype / End-to-End Demo

You are acting as a senior backend architect, staff-level Python engineer, workflow orchestration engineer, AI systems engineer and application security reviewer. Your task is to inspect and extend the **existing Vadiras Flow repository** to deliver a reliable, demonstrable backend prototype.

The authoritative requirements are in `Vadiras_Flow_Backend_Technical_Spec_v1.md` (or the supplied technical specification file). Read it fully before making changes. If the file is not present in the repository/workspace, use the specification included in the task context and create a local project documentation copy only if appropriate.

# 1. Non-negotiable instructions

1. **This is an existing repository. Do not create a replacement project or overwrite it blindly.** Inspect the current codebase first.
2. Preserve working functionality, naming conventions, package manager, migrations, tests, and architecture where reasonable. Prefer incremental changes.
3. Do not delete files/data, rewrite Git history, force-push, remove tests, overwrite `.env`/secrets, or run destructive migrations. Ask before irreversible operations.
4. Never invent successful test results. Run the tests and report the actual command, result and failures.
5. Do not put API keys, GitHub private keys, JWT secrets, webhook secrets or passwords in code, prompts, fixtures or frontend bundles.
6. Do not execute code generated by an LLM. Workflow execution must use registered, schema-validated node types only. No `eval`, generated Python, shell commands or arbitrary dynamic imports from model output.
7. LLM output is untrusted. Validate it against strict schemas and independently authorize every side-effecting action in backend code.
8. Never let an agent grant itself permissions, edit policies, create credentials, approve its own task or bypass the Policy Engine.
9. Use Temporal Workflow code only for deterministic orchestration. Put database, HTTP, GitHub and LLM calls in Activities.
10. A tool/API success response does not automatically mean the business request is resolved. Implement read-back verification and evidence.
11. All important domain data/events must be organization-scoped. External customer identities must not see internal-only content or other customers' requests.
12. Do not introduce infrastructure or dependencies not justified by the specification. In particular, do not add Redis, Kafka, Kubernetes or multiple microservices by default.
13. Do not hard-code an LLM vendor. Build a provider abstraction and deterministic Mock Provider first. A real provider is configured only through environment/settings.
14. The chosen agent topology is a **bounded supervisor-managed swarm**, not free-form autonomous peer-to-peer agents.
15. If a requirement conflicts with existing architecture, explain the conflict, choose the smallest safe adaptation, and document the decision.

# 5. Target domain architecture

Implement/reuse these logical modules. They may be packages within a modular monolith; do not split them into microservices without a demonstrated need.

- Identity & Organization: users, employee/customer-contact kind, departments, memberships, roles and permissions.
- Request Intake: create/list/detail/update requests, attachments/messages if existing, normalization and classification.
- AI Intelligence: provider adapter, request analyst, bounded specialist swarm, planner, critic and verifier assistance.
- Workflow Designer: declarative JSON graph, node registry, graph validation, versioning and publish lifecycle.
- Agent Orchestrator: agent registry, capability checks, task dispatch and structured outputs.
- Governance: RBAC/resource scope, deterministic policy checks, risk, approval binding and per-action execution guard.
- Workflow Runtime: Temporal workflows/activities, DAG scheduling, timers, signals, pause/resume/cancel, retries and bounded adaptation.

- Verification: postconditions, read-back, evidence and explicit final outcomes.
- Observability: execution events, audit, SLA, usage/cost and metrics.
- Memory: pgvector retrieval with organization and authorization filters.

The core principle is: **LLM proposes; Policy Engine authorizes; Temporal/runtime executes; Verification proves.**

# 6. Bounded multi-agent swarm implementation

Implement logical specialist agents. They may use the same LLM model initially, but must have separate role instructions, input/output schemas and capability boundaries.

Required roles:

1. Supervisor/Orchestrator — delegates, collects, resolves conflicts, produces a proposal.
2. Request Analyst — intent, request category, entities, missing information and priority recommendation.
3. Technical Analyst — technical dependencies and task decomposition.
4. Operations Analyst — department routing, workload and SLA considerations.
5. Security/Risk Analyst — risk flags, sensitive data and permission concerns.
6. Workflow Planner — candidate workflow JSON.
7. Critic/Reviewer — checks contradictions, missing steps and unsafe assumptions.
8. Executor Worker — performs a specifically authorized connector/tool action through the Tool Broker.
9. Verification Worker — gathers evidence; it cannot self-approve or change workflow policy.

Required behavior:

- Parallelize independent analysis tasks.
- Structured JSON output only for inter-agent messages.
- Supervisor-mediated dispatch; do not build unrestricted agent-to-agent calls.
- Maximum review/debate rounds default 2; make configurable.
- Bounded concurrency, duration and cost/token budgets.
- Conflict resolution must treat policy/security blockers as hard constraints, not majority-vote preferences.
- Store concise decision summary, assumptions, evidence references and agent outputs. Do not store or expose hidden chain-of-thought.
- Agents must not have general direct database access or unrestricted network tools.
- All action calls route through the Tool Broker and Policy Engine.

# 7. AI provider abstraction

Create a provider-neutral interface that supports at least:

- structured generation (JSON/schema constrained when supported);
- plain completion if needed for summaries;
- optional tool-call proposal output (the backend still validates and authorizes it);
- model/provider metadata;
- timeout/retry/error normalization;
- usage/token/cost metadata where available.

Implement `MockLLMProvider` first so tests and demo can run without API credentials. Read real provider configuration from environment variables. Do not select a vendor in code. Do not assume all providers support the same structured-output or tool-calling behavior; expose capabilities and validate provider responses.

Version prompts and schemas. Limit automatic JSON repair attempts. Invalid model output must fail safely or request human clarification, not silently fabricate fields.

# 8. Workflow DSL and validation

Use a versioned declarative JSON graph. Initial node types:

`TRIGGER`, `CLASSIFY`, `AI_ANALYSIS`, `CONDITION`, `AGENT_TASK`, `HUMAN_TASK`, `APPROVAL`, `CONNECTOR_ACTION`, `WAIT_EVENT`, `NOTIFICATION`, `VERIFICATION`, `END`.

Every node must have a registered Pydantic configuration schema and typed input/output contract. Edges define dependencies and optional safe conditions. No arbitrary code in node config.

Validate:

- node/edge references and unique IDs;
- allowed node types;
- graph reachability and cycle rules (reject cycles unless a specific bounded loop node is implemented later);
- input/output compatibility and required data;
- connector/agent capability availability;
- permission/resource scope;
- policy, risk and required approval;
- max node count, runtime, retry, parallelism and cost;
- a verifiable terminal postcondition.

Published workflow versions are immutable. Each run references an exact version ID and content hash. Editing a running graph in place is forbidden.

# 9. Governance and security implementation

Implement RBAC plus resource-scoped checks. Verify organization, membership, active status, actor type, department/team scope, requester/resource relation, permission, connector installation/repository, action type and policy version.

Customer contacts must be able to see only explicitly authorized customer-visible requests/messages/attachments. Internal notes, security findings, audit details and internal workflow tasks are private by default.

Agent identities are service principals. Never inherit all permissions from the requester. Use narrowly scoped task grants. Approval cannot exceed the approver's own authority or organization policy.

Risk-based approval:

- LOW: auto-execute only if all policy, permission and budget checks pass.
- MEDIUM: extra validation or configured manager approval.
- HIGH: explicit authorized approval.
- CRITICAL: block in initial demo or require designated approval and separately configured safe path.

Bind approval to exact workflow version, node, action, parameter hash, resource scope, policy version and expiry. Any material change invalidates approval. Check policy again immediately before every side effect.

JWT requirements:

- short-lived access token;
- maintained JWT implementation and secure password hashing;
- validate signature, expiry and relevant issuer/audience settings;
- do not put secrets or sensitive data in token claims;
- do not trust stale role claims alone for privileged actions;
- use refresh rotation/revocation if refresh tokens are implemented.

# 10. Temporal runtime implementation

Use Temporal for durable workflow execution. Workflow definitions must be deterministic. Keep LLM, HTTP, GitHub, DB and other external I/O inside Activities. Use signals/updates or the repository's compatible Temporal SDK mechanism for approvals and external events. Use Queries/read APIs for status where appropriate.

Implement:

- request/workflow orchestration;
- node dependency scheduling and bounded parallelism;
- wait-for-approval and wait-for-event behavior;
- retries, timeout, cancellation and pause/resume;
- external event correlation;
- durable progress and recovery;
- execution state persistence to domain DB;
- activity idempotency and reconciliation before repeating side effects.

Do not assume Temporal retries make external side effects exactly-once. Use idempotency keys and connector operation records. Keep business state and evidence in PostgreSQL; Temporal history is not a replacement for domain/audit tables.

Default demo bounds, configurable:

- max 2 replan attempts per run;
- max 3 retries per retryable activity;
- max 4 concurrent specialist analyses;
- finite per-node and per-run timeouts;
- bounded connector rate and LLM budget.

A replan must produce a proposal/new version. It cannot silently expand permissions, target resources, irreversible actions or risk class. Escalation pauses and requests approval.

# 11. GitHub App and connector implementation

Create a connector interface and a GitHub App adapter. Prefer minimum required installation permissions:

- repository metadata read;
- Issues read/write only for the operations the demo actually performs;
- subscribe only to the required `issues` and optionally `issue_comment` webhook events.

Do not request broad Contents, Administration, Actions, Deployments or organization-level permissions unless a proven demo feature requires them.

Implementation requirements:

- installation-scoped token generation/cache/refresh; never expose token to frontend or prompt;
- allow-list installation repositories;
- validate connector permission and resource scope before each action;
- webhook HMAC-SHA256 verification against raw body using constant-time comparison;
- deduplicate by GitHub delivery ID;
- persist webhook inbox before async handling;
- validate installation/repository/resource scope;
- treat payload content as untrusted;
- webhook-first behavior with a conservative polling/reconciliation fallback;
- handle rate limits, transient errors and token expiry;
- Mock GitHub connector for tests and local demos.

Start with Issue read/create/update/assign/comment as explicitly permitted. Do not implement production deploy or arbitrary repository write capabilities for the demo.

# 12. Verification, evidence and audit

Use explicit outcomes: `VERIFIED`, `PARTIALLY_VERIFIED`, `FAILED`, `UNVERIFIED`.

Each material action needs an expected postcondition and evidence source. Read the resource back after side effects. For example, after creating an Issue, verify the correct repository, issue number and required fields. Issue closure alone is not proof that a bug is fixed; require configured technical evidence or an authorized human confirmation.

Store actor, action, resource, timestamp, organization/request/run/node context, policy decision/version, approval reference, result and evidence reference in an append-only audit/event design. Never log secrets or hidden chain-of-thought. Redact sensitive data.

# 13. Memory and analytics

Use PostgreSQL + pgvector. Memory classes: request, workflow, execution, knowledge and feedback. Retrieval must filter by organization, access classification, department, validity, request type and source status. Vector similarity must not bypass authorization filters.

Only promote completed patterns to reusable success memory after a verified result or authorized human review. Memory is advisory in the demo; do not let it auto-edit policies or workflows.

Expose metrics for:

- SLA compliance and resolution time;
- automation rate and workflow success;
- verified resolution rate;
- human intervention and approval latency;
- agent performance/failure/retry;
- LLM and connector cost (mark estimated/unknown honestly);
- audit activity;
- department workload and industry/domain dimensions.

Document formulas/denominators. Do not label an estimated cost as actual provider billing.

# 16. Testing and acceptance criteria

At minimum add/run:

**Unit tests:** schema validation, workflow graph validation, policy evaluation, scope enforcement, risk/approval, agent routing, idempotency, event deduplication, verification, memory filtering.

**Integration tests:** clean migrations, auth/RBAC, Temporal execution with mock activities, approval wait/resume, retries/timeouts, GitHub adapter mock, webhook signature validation, outbox recovery.

**E2E tests:**
1. All five request types can be submitted and classified.
2. Bounded swarm returns structured, traceable outputs.
3. At least one request completes Request -> Analyze -> Plan -> Validate -> Approve (if needed) -> Execute -> Verify -> Audit.
4. Change Request blocks before protected action until approved.
5. Unauthorized agent action is blocked even if LLM proposes it.
6. Customer contact cannot view another customer's or internal-only request.
7. Duplicate request/webhook does not create duplicate side effects.
8. Simulated failure triggers bounded retry/reassignment/replan and never escalates permission silently.
9. API/worker restart leaves workflow resumable.
10. Frontend can render request, workflow, validation, execution events, approval and verification from backend contracts.

Use MockLLM and MockGitHub in CI/local tests. Tests must not require paid API credentials.
